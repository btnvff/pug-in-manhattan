# Codex repository instructions

- Treat the current repository files and Git evidence as the source of truth, not old chat context or historical branches. Read `PROJECT.md` before every substantial task and `README.md` for setup and usage. Resolve dated status notes against current evidence; do not assume they describe today's branch or deployment.
- Read `PUG-WORLD-RATIO.md` before world, camera, perspective, scale, viewport or composition changes. Read `CHARACTER_REVIEW.md` before pug, model, material or animation changes; read both when their scopes overlap.
- Preserve the FULL-3D WebGL 2 / local Three.js architecture, explicit classic `defer` script order, simulation/presentation separation, single-view lifecycle and resource ownership. Preserve gameplay, RNG draw order, controls, Russian UI and portrait composition unless the task explicitly changes them.
- The standalone 2D world/pug/food renderer, view selector and old-game fallback are intentionally retired. Never restore them. Preserve required Canvas overlays/effects, drawing primitives, diagnostics and procedural textures used by the 3D game. Preserve the controlled graphics-error/reload path.
- Prefer one small, focused change at a time. Avoid unrelated refactors, file splitting for size alone, new frameworks, npm, bundlers, app ES modules and runtime CDNs. Preserve existing GitHub Pages publication; do not add unnecessary CI/workflows or revive historical workflows to bypass environment restrictions.
- Inspect the working tree, branch and current remote `main` before work; if network access prevents confirmation, report that limitation. Protect existing local changes and identify the latest known-good playable rollback commit from repository evidence before risky work. Never reset newer work to an older documented baseline; documentation-only commits do not replace a verified runtime baseline.
- Use targeted verification from `PROJECT.md`: character checks for pug changes, WorldRatio checks for world/camera changes, gameplay/RNG checks for simulation changes, and relevant browser/visual checks for affected behavior. Broaden only when scope or a regression warrants it. Documentation-only changes need path/link checks and diff review, not expensive unrelated suites. Investigate failures; environment-blocked checks are not passes or reasons to rewrite the game.
- Determine the current game version from `index.html`'s `#build-version`; keep CSS/JS/manifest `?v=` cache keys aligned. Increment PATCH only for a completed, verified user-visible iteration or behavior fix, never for audits, documentation-only changes or unfinished/failed attempts. Follow the separate WorldRatio versioning rules; retain locked fixtures rather than rewriting them to pass.
- Report states separately: **LOCAL** = working tree, branch, commit and local verification; **MAIN** = confirmed remote `main` revision; **PRODUCTION** = confirmed Pages deployment revision and live verification. A local commit, push or merge does not prove deployment; remote HEAD does not identify loaded production bytes.
- Never claim tests, commit, push, merge, deployment or production verification succeeded without confirming the corresponding result. State what passed, failed, was blocked or was not run. Keep dated evidence distinct from fresh verification; offline browser checks do not prove production or physical-device behavior.
- Follow the user's publication authorization. Commit/push permission does not authorize merge or history rewriting. If GitHub/network publication fails, preserve completed local work and its verification; retry only the failed publication step instead of reimplementing the feature.
- Keep permanent decisions and contracts in the existing `PROJECT.md`, `PUG-WORLD-RATIO.md`, `CHARACTER_REVIEW.md` and `README.md` as appropriate to the task. Avoid competing specifications or relying on chat as the only record.
